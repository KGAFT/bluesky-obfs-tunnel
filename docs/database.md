# MariaDB authentication and Docker

The server uses Diesel's MySQL backend to store client credentials and replay
timestamps in MariaDB. It requires a database; there are no static server
credentials or in-memory fallback. The Docker image contains only the server.
Run clients natively as before.

## Start with Docker Compose

Copy `.env.example` to `.env` and replace `MARIADB_PASSWORD` with a random hex
password, for example one generated by `openssl rand -hex 32`. A hex password
does not need URL escaping. Other passwords must be percent-encoded in
`DATABASE_URL`; the database itself must receive the original password.

```sh
cp .env.example .env
cp config/server.example.json config/server.json
chmod 600 .env config/server.json
# Set MARIADB_PASSWORD and TUNNEL_UID/TUNNEL_GID in .env before continuing.
# Root login: keep container IDs 1000:1000 and chown -R 1000:1000 config.
# Customize config/server.json (and match the client obfuscation settings).
docker compose -f compose.yaml -f compose.build.yaml build server
docker compose up -d --wait db
```

Create each client explicitly. This command reads its password without echoing
it, runs the server's administrative command, and exits without a listener or
cover-site handshake:

```bash
read -r -s -p 'Client password: ' CLIENT_PASSWORD
echo
export CLIENT_PASSWORD
docker compose run --rm -e CLIENT_PASSWORD server --create-client alice
unset CLIENT_PASSWORD
docker compose up -d server
docker compose logs -f server
```

Set `client_identity` to `alice` and `client_password` to the password you chose
in your local `client.json`. Change the client example's public password and
server ID on both peers for deployment. Use `test-client` and the client
example's password if you want to run the existing demonstration commands.

The server automatically runs embedded Diesel migrations on startup and before
client creation. No Diesel CLI or SQL seed script is required. Duplicate
identities fail without overwriting credentials or resetting replay history.
Identities contain 1–255 UTF-8 bytes and are case sensitive. Passwords contain
1–65535 UTF-8 bytes. Whitespace-only values are rejected.

The base Compose file uses a prebuilt server image with `pull_policy: never`.
Build it locally with `compose.build.yaml` as shown above, or load the image
from the [VPS bundle](vps-deployment.md). The base file contains no build context,
so client creation and restarts also work on a VPS without source code.

The supplied Compose file uses the official MariaDB 11.4 image, waits for its
healthcheck, publishes tunnel port 443, and keeps MariaDB private to the Compose
network. `mariadb_data` persists credentials and timestamps across restarts and
image rebuilds. `docker compose down` preserves that volume; adding `--volumes`
deletes it. Changing `.env` does not rotate passwords in an existing database.

`SERVER_CONFIG` selects the server JSON mounted read-only at `/app/server.json`.
The supplied `.env.example` selects `config/server.json`; copy and customize the
example there before startup. Without that variable, Compose uses
`config/server.example.json`. Keep multiplexed forwarding and the listener
on `0.0.0.0:443`; `TUNNEL_PORT` selects the host's published port. Container
loopback destinations refer to the server container. Configure reachable
destinations when forwarding to services running on another host or container.
The server still needs access to the configured cover site during handshakes
(`www.microsoft.com:443` with the Chrome 149 defaults).

Compose mounts `config/` writable at `/app/config` and uses it as the server's
working directory. With the default relative pattern paths, the server loads
`config/cli_pattern.bin` and `config/serv_pattern.bin` on the host, or captures
and saves them there if missing or invalid. The JSON is still loaded through
the read-only `/app/server.json` mount.

Set `TUNNEL_UID` and `TUNNEL_GID` in `.env` to the host owner of `config/`
(run `id -u` and `id -g` if you own it); both default to 1000. That user must
own the private `server.json` (mode `0600`) and have write permission on the
directory and any existing pattern files. When deploying as root with the
default container IDs, run `chown -R 1000:1000 config` as root after copying or
extracting files. See the [permission repair steps](vps-deployment.md#fix-config-permission-errors)
for other configured IDs and a check inside the container. Pattern
files may be absent at startup. To reuse the shipped Chrome 149/Microsoft pair,
copy both root `cli_pattern.bin` and `serv_pattern.bin` into `config/` before
starting the server; otherwise retrieve the captured pair from there for clients.
Existing valid patterns are reused; changing capture settings alone does not
regenerate them. After replacing patterns,
recreate the server with
`docker compose up -d --no-build --force-recreate server` and distribute the
matching pair to clients.

## Native server and database tests

For a database reachable only from the host's loopback interface:

```sh
docker compose -f compose.yaml -f compose.local.yaml up -d --wait db
```

Set `DATABASE_URL` to `mysql://tunnel:PASSWORD@127.0.0.1:3306/tunnel`, using the
same password as `.env`. Build with the MariaDB development library installed
(`libmariadb-dev` on Debian/Ubuntu, plus the project's existing native build
dependencies). Then create a client and start the server:

```bash
read -r -s -p 'Client password: ' CLIENT_PASSWORD
echo
export CLIENT_PASSWORD
cargo run -- --create-client alice
unset CLIENT_PASSWORD
cargo run -- --multiplexed
```

Use `MARIADB_LOCAL_PORT` to choose another host database port. The server JSON's
`database` settings select the URL environment variable (`DATABASE_URL`), maximum
pool size (8), and pool acquisition timeout (5 seconds). Diesel work runs on
Tokio's blocking pool. Startup database/migration failures stop the server;
authentication database failures reject the attempt.

Run the integration test against a disposable database:

```sh
TEST_DATABASE_URL="$DATABASE_URL" cargo test --lib \
  server::auth::tests::mariadb_credentials_reject_replays_across_connections_and_restarts \
  -- --ignored
```

The test applies migrations and checks creation, duplicate rejection, unknown
and case-sensitive identities, stale/future timestamps, repeated and decreasing
timestamps, persistence after reopening the pool, and concurrent reservations
from independent pools. Its test row is removed on success.

## Replay behavior and credential storage

Each credential lookup locks the client's InnoDB row in a transaction, checks
the timestamp against the current clock and `last_auth_ms`, then persists the
new timestamp before returning the password to the codec. Equal or older
timestamps and clock skew larger than `replay_guard_window_ms` are rejected.
The window defaults to 60000 ms and must be positive. Keep peer clocks in sync.
All server instances sharing the database share the same replay history. Two
attempts for one identity with the same millisecond timestamp cannot both pass.

The codec separately verifies the client's password through SPAKE2 and retains
its nonce replay guard. Its provider API runs **before** password proof is
verified and has no success callback. Consequently `last_auth_ms` records a
reserved authentication attempt, not a confirmed successful login. A failed or
cancelled handshake consumes that timestamp too. Attempts must use a newer
timestamp on retry; a permitted future timestamp may delay retries until the
client clock catches up, bounded by the configured skew window.

SPAKE2 requires retrieving the original password, so the database stores it as
a secret rather than a one-way login hash. Protect database access and backups.
Existing JSON `clients` arrays are rejected: remove that field and create the
clients with `--create-client`. Do not clear timestamps or recreate clients
during routine startup. Migrations run at startup; serialize initial startup
when introducing a schema migration to multiple server replicas.
