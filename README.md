# bluesky-obfs-tunnel
# Warning this is vibecoded
The server now requires **MariaDB**, using **Diesel** for client credentials and
durable replay timestamps. See [database and Docker setup](docs/database.md) to
start MariaDB and the server with Docker Compose and create clients with
`--create-client ID`. Only the server is packaged into the Docker image;
clients run natively. Complete that setup before using the examples below.

To build the server locally and upload it to a VPS without compiling there,
run `bash scripts/build_vps.sh linux/amd64` (or `linux/arm64`) and
follow the [precompiled server deployment guide](docs/vps-deployment.md).
The base Compose file runs prebuilt images; `compose.build.yaml` enables local
source builds. Existing deployments should follow the guide's migration checklist.

See [the project structure guide](docs/project-structure.md) for the module map,
where to add code, and the 300-line source-file limit. Check file sizes with
`python3 scripts/check_file_lengths.py`.

Both binaries support `--config PATH` (or `--config=PATH`) for validated JSON
settings. Missing files are created using defaults; invalid files stop startup.
See [configuration and reconnecting](docs/configuration.md) for all fields and
the complete [server](config/server.example.json) and
[client](config/client.example.json) examples. Proxy sessions rotate after a
random 30–40 minutes by default; the interval and retry delay are configurable.
Rotation closes existing streams while keeping the local proxy listener bound.

## Create clients and start the server

From the project root, copy the Compose environment example and set
`MARIADB_PASSWORD` in `.env` to a random hex password, such as one generated by
`openssl rand -hex 32`. This is the database password; each tunnel client gets
its own identity and password in the next step.

```sh
cp .env.example .env
cp config/server.example.json config/server.json
chmod 600 .env config/server.json
# Edit .env and config/server.json before continuing.
# Non-root login: set TUNNEL_UID/TUNNEL_GID to id -u / id -g; choose a DB password.
# Root deployments: keep container IDs 1000:1000 and chown -R 1000:1000 config.
docker compose -f compose.yaml -f compose.build.yaml build server
docker compose up -d --wait db
# Seed the writable config/ directory with the matching shipped pattern pair.
cp cli_pattern.bin serv_pattern.bin config/
```

Create a client named `alice` using the server's administrative command. In
Bash, read the client password without displaying it, then pass it through
`CLIENT_PASSWORD`:

```bash
read -r -s -p 'Client password: ' CLIENT_PASSWORD
echo
export CLIENT_PASSWORD
docker compose run --rm -e CLIENT_PASSWORD server --create-client alice
unset CLIENT_PASSWORD
```

The command saves the credentials in MariaDB and exits. It applies database
migrations automatically and does not start a tunnel listener. Repeat it with
a different identity to create another client. Identities are case sensitive;
an existing identity is rejected without changing its password or replay history.
There are no automatically created clients or server JSON `clients` entries.

Start the tunnel server:

```sh
docker compose up -d server
```

Set these fields in your local `client.json`, replacing the password with the
one entered above and the server address if it runs on another host:

```json
{
  "server_address": "127.0.0.1:443",
  "client_identity": "alice",
  "client_password": "the-password-you-entered"
}
```

Other omitted fields use their defaults. For the supplied multiplexed server,
run the native client as a local HTTP/HTTPS proxy:

```sh
cargo run --bin client -- --config client.json --http-proxy 127.0.0.1:8080
```

To use the existing demonstration client credentials, create `test-client`
instead of `alice` and enter `HelloPasswordForHandshake` at the password prompt.
For a native server, set `DATABASE_URL` and run
`cargo run -- --create-client alice` while `CLIENT_PASSWORD` is exported.
See [database setup](docs/database.md) for native build requirements, local
database access, custom configuration, and replay behavior. Credentials and
timestamps persist in the Compose database volume across restarts.

## Using the client

For an ARM64 Android executable to run inside Termux, see the
[aarch64 Termux build and run instructions](docs/termux.md). The build script
packages the client, pattern files, and example settings into a transfer archive.

The `client` binary can send a test payload or listen as a local HTTP proxy.
Test requests write the response bytes to stdout.
Run it from the project directory so it can load `cli_pattern.bin` and
`serv_pattern.bin`. It uses the credentials, cover site, public password, and
server ID from the default configuration; create its `test-client` credential
in MariaDB first. The server needs
access to `www.microsoft.com:443` during the real `FakeCodec` handshake, even when
testing local destinations.

To listen on a local TCP port and forward every connection through the tunnel,
start the server and client in separate terminals:

```sh
./bluesky-obfs-tunnel --bind 0.0.0.0:443 --multiplexed
./client --server 127.0.0.1:443 --listen 127.0.0.1:1080 --tcp 127.0.0.1:2080
```

After `cargo build --bins`, invoke `./target/debug/bluesky-obfs-tunnel` and
`./target/debug/client` from the project root so patterns resolve correctly, or
use `cargo run --bin NAME -- OPTIONS` there. The client listens on
port 1080; each accepted connection opens a separate TCP stream to port 2080 on
the **server's** loopback interface. Choose any available local listening port
with `--listen IP:PORT`. Traffic is relayed unchanged, so this also exposes a
remote SOCKS or HTTP proxy locally. For a SOCKS proxy on server port 2080, test
with `curl --noproxy '' --proxy socks5h://127.0.0.1:1080 https://example.com/`.

The listener supports concurrent connections and TCP half-closes. It stays bound
while reconnecting or rotating sessions; existing connections close on rotation.
`--timeout` limits setup and destination opening, not established streams.
`--listen` requires `--tcp` and cannot be combined with proxy or payload options.
Without `--listen`, `--tcp` retains its one-shot payload behavior.

The server's listener and fixed destination can also be chosen on the CLI:
`./bluesky-obfs-tunnel --bind 0.0.0.0:9443 --tcp 127.0.0.1:2080`.
This selects fixed TCP mode; `--tcp` and `--multiplexed` are mutually exclusive
on the server. CLI overrides are not saved to JSON; restart to change addresses.

To test the default fixed TCP mode, start a local HTTP target and the tunnel
server in separate terminals:

```sh
python3 -m http.server 2080 --bind 127.0.0.1
cargo run --bin bluesky-obfs-tunnel
```

Then send an HTTP request through the tunnel (Bash quoting preserves CRLF):

```sh
cargo run --bin client -- --message $'GET / HTTP/1.0\r\nHost: localhost\r\n\r\n'
```

To choose a destination, start the server with `cargo run -- --multiplexed`, then
run either of these against an appropriate TCP or UDP target:

```sh
cargo run --bin client -- --tcp 127.0.0.1:2080 \
  --message $'GET / HTTP/1.0\r\nHost: localhost\r\n\r\n'
cargo run --bin client -- --udp 127.0.0.1:5353 --message 'hello'
```

For a local UDP echo target, run this in another terminal:

```sh
python3 - <<'PY'
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("127.0.0.1", 5353))
while True:
    data, peer = sock.recvfrom(65535)
    sock.sendto(data, peer)
PY
```

Use `--server HOST:PORT` to test a remote tunnel, `--file PATH` for binary input,
and `--message ''` for an empty UDP datagram. With no payload option, the client
sends `hello from client` followed by a newline. TCP half-closes its write side
and reads until EOF; UDP sends one datagram and waits for one reply, preserving
empty datagrams and enforcing the 8192-byte limit. Each test request has a
30-second timeout, configurable with `--timeout SECONDS`. Diagnostics go to
stderr and failures return a nonzero exit status. `--setup-port PORT` changes the
client's local handshake proxy port if 7756 is busy. Run
`cargo run --bin client -- --help` for all options.

For a local HTTP proxy, start the multiplexed server and the client in separate
terminals:

```sh
cargo run -- --multiplexed
cargo run --bin client -- --http-proxy 127.0.0.1:8080
```

Then configure your browser's HTTP and HTTPS proxy to `127.0.0.1:8080`, or use
curl (the empty `--noproxy` value also sends localhost requests through it):

```sh
curl --noproxy '' --proxy http://127.0.0.1:8080 http://127.0.0.1:2080/
curl --noproxy '' --proxy http://127.0.0.1:8080 https://example.com/
```

The listener shares one authenticated tunnel across concurrent browser
connections. Plain HTTP URLs are rewritten to origin paths and each response
closes that browser connection. Request bodies stream without being buffered in
full, including chunked uploads and `Expect: 100-continue`. HTTPS uses CONNECT;
the proxy confirms it only after the server opens the destination and preserves
any TLS bytes read alongside the CONNECT headers. The server resolves and
checks all destinations using its `ConnectPolicy`.

Proxy mode runs until Ctrl-C and reconnects after failures or scheduled rotation.
`--timeout SECONDS` limits tunnel setup, each browser's header read, and each
destination open. Established streams close when their tunnel rotates.
The listener defaults to 256 concurrent connections and
headers up to 16 KiB. Slow or malformed clients and failed destinations affect
their own connection. This mode requires `--multiplexed` on the example server
and cannot be combined with `--tcp`, `--udp`, `--message`, or `--file`.

`ForwardServer` accepts obfuscated TCP connections, performs the `FakeCodec`
handshake, and runs one `ClientSession` per client. Choose the destination mode
in `src/bin/server/main.rs` when calling `ForwardServer::new`:

```rust
// Forward a byte stream to a fixed TCP destination (the current example).
ForwardTo::Tcp(TcpConnection::new("127.0.0.1".parse()?, 2080))

// Forward datagrams to a fixed UDP destination.
ForwardTo::Udp(UdpConnection::new("127.0.0.1".parse()?, 2080))

// Serve the existing multiplexed HTTP proxy protocol.
ForwardTo::HttpProxy(ConnectPolicy::default())

// Let one client open multiple TCP and UDP destinations.
ForwardTo::Multiplexed(ConnectPolicy::default())
```

Import `UdpConnection` from `server::udp_connection` and `ConnectPolicy` from
`server::connect_policy` as needed. Each server listener selects one mode; run
separate listeners to offer different wire modes. `Multiplexed` serves both TCP
and UDP through the same listener and client tunnel.

For TCP mode, decoded tunnel frames carry raw stream bytes. Responses are split
into chunks of at most 8192 bytes. A client write half-close shuts down the target
write side while allowing the target's remaining response to reach the client.

For UDP mode, the tunnel transport is still TCP. Each decoded frame carries one
complete UDP datagram; each target datagram produces one response frame. Clients
must preserve these boundaries and limit datagrams to 8192 bytes. Larger
datagrams terminate the session with an error rather than being split or
truncated. Empty datagrams are supported. Each client gets a separate connected
UDP socket, with IPv4 or IPv6 selected from the destination address.

HTTP proxy mode accepts the original `Connect((id, "host:port"))` and
`HttpPacket(id)` frames, with replies tagged by the same stream ID. It supports
plain HTTP and HTTPS CONNECT traffic relayed by the existing client. This mode
is the server side of the tunnel protocol; an HTTP proxy listener belongs on
the client side. The original wire layout is preserved. Removed interface
protocol tags are rejected and have no handlers or networking dependencies.

`ConnectPolicy::default()` permits local destinations, matching the original
session. Use `ConnectPolicy::new(false, &allowlist, &public_ips)` to restrict
proxy destinations, while allowing specific `host:port` entries. DNS is resolved
and filtered before connecting.

Use `ForwardServer::with_limits(StreamLimits { ... })` to configure response,
endpoint event, and endpoint input queues. Queue depths are clamped to at least
one. An endpoint input queue overflow reports `FailedEndPoints` and closes that
endpoint. Failed connects and endpoint EOF also report `FailedEndPoints`.
Disconnecting a client cancels its outstanding connects and endpoint tasks.

Run `cargo test` for local TCP/UDP forwarding, HTTP multiplexing, shutdown,
queue bounds, and compatibility with the original HTTP wire format. Session
tests use a length-delimited test codec and local target sockets; they do not
perform a `FakeCodec` authentication handshake.

A single client can also open multiple TCP and UDP destinations over the same
obfuscated connection. Start the example server in this mode with:

```sh
cargo run -- --multiplexed
```

In your own server, select `ForwardTo::Multiplexed(ConnectPolicy::default())`.
Then use the library API:

```rust
use bluesky_obfs_tunnel::{client::ForwardClient, server::StreamLimits};
use tokio_util::bytes::Bytes;

// cfg_client is a FakeCodecCfg with the client pattern and
// CredentialsSide::Client credentials matching the server's configuration.
let (client, driver) = ForwardClient::connect(
    cfg_client, "127.0.0.1:443", StreamLimits::default(),
).await?;

let (mut tcp1, mut tcp2, mut udp1, mut udp2) = tokio::try_join!(
    client.open_tcp("127.0.0.1:8080"),
    client.open_tcp("127.0.0.1:8081"),
    client.open_udp("127.0.0.1:5353"),
    client.open_udp("127.0.0.1:5354"),
)?;

tcp1.send(Bytes::from_static(b"request one")).await?;
tcp2.send(Bytes::from_static(b"request two")).await?;
udp1.send(Bytes::from_static(b"datagram one")).await?;
udp2.send(Bytes::from_static(b"datagram two")).await?;
let replies = tokio::try_join!(tcp1.recv(), tcp2.recv(), udp1.recv(), udp2.recv())?;

// Dropping or closing a connection releases only its own endpoint.
tcp1.close().await?;

client.shutdown().await?;
driver.await??;
```

Each open waits for the server's connection acknowledgement. A UDP open creates
a connected socket; it does not confirm that an application is listening on the
remote UDP port. Destinations are resolved on the server and checked with its
`ConnectPolicy` for both TCP and UDP.

`send()` and `recv()` work with `Bytes`. TCP is a byte stream, so a receive chunk
may combine or split sends. TCP sends are chunked automatically. UDP preserves
one datagram per send and receive, including empty datagrams; its size limit is
8192 bytes. `recv()` returns `None` at read EOF, while an empty UDP datagram is
`Some(Bytes::new())`. `send()` completes when data enters the tunnel writer
queue; it does not acknowledge remote application consumption.

Use `connection.split()` to obtain a cloneable `ForwardSender` and a
`ForwardReceiver` for simultaneous sending and receiving. TCP supports
`shutdown_write()` while continuing to receive replies. Dropping both halves
closes the logical connection. The `ForwardClient` handle is also cloneable.
Cancelling an open cancels its server endpoint. The driver finishes when all
client and connection handles are dropped, or after `shutdown()`. Normal tunnel
shutdown drains final replies and waits up to 10 seconds for the server to close.

The client command and writer queues use `sink_queue_depth`, and each connection's
receive queue uses `max_pending_frames`. A full receive queue closes that
connection and reports an error after its buffered data, leaving the other
connections running. A failed endpoint or oversized UDP response also affects
only that connection. Aborting the driver task closes the entire tunnel.
The mixed client mode requires a `Multiplexed` server; the original raw fixed
TCP/UDP modes and HTTP proxy mode keep their existing behavior and wire format.
